## Boundary rules

- `app/` stays thin: compose features, prefetch data, declare page caching (`"use cache"` + `cacheLife` + `cacheTag`, see `docs/state-management.md`), no business logic. Suspense boundaries and fallbacks belong to the feature's component, not the route file (`docs/code-style.md`).
- A new page goes in `app/(public)/` unless it needs a signed-in reader; then it goes in `app/(authorized)/`. The group's layout enforces nothing — placing a page there does not protect it. Each page's feature component calls `requireSession()` (from `@/features/auth`) inside its own Suspense boundary before reading any reader data: it redirects a signed-out reader to `/login`, and returns `unknown` when Supabase can't be reached, which the page shows as "service unavailable" instead of redirecting. Never a layout-only check, since a shared layout does not re-render on client navigation. On top of that, the proxy redirects a signed-out page request under `/account` before anything renders (ACCOUNT_PATH in `shared/config/account-paths.ts`; a page outside it gets only its own gate). That redirect is optimistic, so the page gate always stays. Route handlers under `app/api/` stay outside both groups.
- Import a feature only through its public API: `@/features/poems`, never `@/features/poems/model/...` (enforced by `no-restricted-imports` in `eslint.config.mjs`).
- Features must not import from other features' internals. If two features need the same thing, move it to `shared/` or compose them in `app/`.
- A feature may import another feature's public API for a server-only accessor it needs, e.g. `authors` takes `getSessionState` / `getCurrentUserId` / `requireSession` from `@/features/auth`, `breadcrumbs` takes `getPublicAuthorName`, `AUTHORS_PAGE_TITLES` and the authors path constants from `@/features/authors`, `getAuthorPoem` and `POEMS_SEGMENT` from `@/features/poems`, `getOwnPoemTitle`, `POEM_MANAGEMENT_TRAIL_LABELS`, `NEW_POEM_PATH`, `EDIT_SEGMENT` and `ownPoemPath` from `@/features/poem-management` (the `own-poem` and `own-poem-edit` matches for `/account/poems/<uuid>` and its `/edit` page share the page's reads, so page and trail can't disagree), and `getOwnCollectionTitle`, `COLLECTION_TRAIL_LABELS`, `NEW_COLLECTION_PATH`, `COLLECTIONS_SEGMENT`, `COLLECTION_EDIT_SEGMENT`, `COLLECTION_POEMS_SEGMENT` and `collectionPath` from `@/features/collection-management` (same shared read for the collection, its edit page and its poems page), `poems` takes `getPublicAuthorName` and `authorPagePath` from `@/features/authors`, and `poem-management` takes `requireSession` / `getSessionState` from `@/features/auth`, `getOwnPublicAuthor` and `AUTHOR_EDITOR_PATH` from `@/features/authors`, and the reads, genres, cache tag, bucket name, `PoemTitleList`, `PoemArticle` and `PoemPageSkeleton` from `@/features/poems`, and `collection-management` takes `requireSession` / `getSessionState` from `@/features/auth` and `getOwnPublicAuthor` and `AUTHOR_EDITOR_PATH` from `@/features/authors`, nothing from `poems` or `poem-management`. `poem-management` and `collection-management` never import each other: the `/account/poems` route passes the collection slots into `MyPoemsPage`, and each keeps its own copy of the leave guard, the leave dialog and the write-log helpers (the import ban in both directions is checked by `collection-management/tests/boundaries.test.ts`). `authors` never imports `poems`, `poem-management` or `collection-management`: the author route passes `AuthorPoemsEntry` into `AuthorPage` as a slot, and the «Управление произведениями» links read `POEM_MANAGEMENT_PATH` from `shared/config`. Only through the index, only server-side (a Client Component may take a type with `import type`, which leaves no runtime import), and never in both directions (no cycles). One client-side exception: `site-footer` renders `contact`'s `ContactDialog`, because the footer always shows that button (`add-contact-form` design D7); `contact` never imports `site-footer`.
- `shared/` never imports from `features/` or `app/`.
- Inside a feature, use relative imports; across layers, use the `@/` alias.
- Don't create a `shared/` abstraction until a second feature actually needs it. Exception: an infrastructure client for an external service (e.g. `shared/lib/contentful`, `shared/lib/supabase`) may live in `shared/lib` from its first consumer.
- `shared/lib/supabase/index.ts` stays client-safe. Its server-only modules start with `import "server-only"` and are imported by subpath: `@/shared/lib/supabase/server` (actions and `dal/`; route handlers reach it through a `dal/` module), `@/shared/lib/supabase/public` (a cookie-less anon client, used only inside a `"use cache"` scope, where reading cookies is not allowed and RLS returns public rows only; anything per reader uses `server`), and `@/shared/lib/supabase/session` (the proxy only). Identity and reader content live in Supabase, editorial pages in Contentful (`docs/decisions/0003-supabase-auth-and-content-split.md`).
- A feature index that exports a server-only module (e.g. `features/auth` exports `confirmSignUp`) is imported only by Server Components and route handlers. The feature's own Client Components import their siblings by relative path, including its `"use server"` actions.

## Naming

- Components: `PascalCase` folder + file (`AuthorPhoto/AuthorPhoto.tsx`, `AuthorPhoto.module.css`, `AuthorPhoto.types.ts`), named exports only (except Next.js route files, which need default exports). A helper only that component uses sits in the same folder in `kebab-case` (`SignInForm/submit-sign-in.ts`). What gets its own file: `docs/code-style.md`.
- Constants: `model/<name>.constants.ts` per feature, `shared/config/constants.ts` project-wide (`docs/code-style.md`).
- Non-component files: `kebab-case` with a role suffix (`poem.types.ts`, `poem.constants.ts`, `greeting.schema.ts`, `auth.actions.ts`; a client-fetched feature adds `<name>.api.ts`, `<name>.queries.ts`, `<name>-ui.store.ts`). Exceptions take no suffix: modules in a feature's `dal/` folder (`dal/home-greeting.ts`), a helper inside a component's folder (`SignInForm/submit-sign-in.ts`, see `docs/code-style.md`), and hooks in a feature's `hooks/` folder, whose `use-` prefix is the role (`hooks/use-profile-field.ts`); a helper only one hook uses sits next to it (`hooks/settle-profile-action.ts`).
- A hook that only one component uses stays in that component's folder. It moves to the feature's `hooks/` once a second component uses it, or when it is part of a contract between components (the author editor's `useProfileField`, `useFieldLock`). Hooks never import from `components/`; the types they share with components live in `hooks/<name>.types.ts`.
- A feature's `actions/` folder holds `"use server"` modules (`<name>.actions.ts`, exporting only Server Actions) and the feature's action client (`action-client.ts`, `import "server-only"`). Server Actions are public endpoints: validate input with a `model/` schema and never export anything else from a `"use server"` module.
- Add `"use client"` only to components that need hooks, state, or browser APIs; keep pages as Server Components.
- Keep domain logic in pure functions under `model/` so it's testable without React.

## Adding a new feature

1. Create `src/features/<name>/{api,model,components}` and `index.ts`.
2. Types in `model/<name>.types.ts`; fetchers in `api/<name>.api.ts`; keys + `queryOptions` + hooks in `api/<name>.queries.ts`. Server-only data for Server Components goes in `dal/<name>.ts` instead (see `docs/decisions/0001-feature-dal-folder.md`).
3. UI state (if any) in `model/<name>-ui.store.ts`.
4. Export only what `app/` needs from `index.ts`.
5. Wire it up in a route under `src/app/`.
